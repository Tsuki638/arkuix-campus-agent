# 接口约定

公共定义以 `app/entry/src/main/ets/contracts/Models.ts`、`Ports.ts` 和 `Calendar.ts` 为准。本文件帮助四人联调；改字段时同步文档与调用方。

## 一、界面调用 Agent

```typescript
interface AgentService {
  createConversation(): Promise<Conversation>;
  send(conversationId: string, text: string, onState?: StateListener): Promise<AgentResult>;
}
```

- `send` 保留会话中的既有上下文；UI 不再自行保存一份用户消息到仓库。
- `AgentResult` 含 `conversation`、`reply`、`state`、`error`；完成时 `error` 为空，失败时显示 `error`。
- 空输入、会话不存在、会话忙和最初历史读写失败会 reject，UI 需 catch 并保留未提交输入。
- 模型/工具循环中的失败返回 `state: 'failed'`，已保存的用户消息可回看；工具执行失败先交回模型，模型可澄清或解释。
- `onState` 是即时界面反馈，不是持久任务状态。当前不承诺任务中断后自动恢复执行。

## 二、Agent 调用模型

```typescript
interface ModelClient {
  complete(messages: ChatMessage[], tools: ToolDefinition[]): Promise<ModelReply>;
}
```

`ChatMessage` 的 `role` 为 `system/user/assistant/tool`，另含 `id`、`content`、`createdAt`、`toolCalls`、`toolCallId`。普通消息的 `toolCalls` 为 `[]`、`toolCallId` 为 `''`。

模型返回纯文本，或返回一个/多个 `ToolCall { id, name, input }`。`input` 是 JSON 字符串，C 负责传递，A 的工具负责实际校验。存在工具请求的 assistant 消息及对应的 tool 消息必须按调用 ID 配对，保持原顺序。

`CompatibleModelClient` 用常见 Chat Completions 工具协议映射这些字段；所选厂商的模型名、完整 HTTPS endpoint、专有参数和工具能力由 C 验证。参考 [阿里云 Model Studio 官方 Function Calling 说明](https://www.alibabacloud.com/help/en/model-studio/qwen-function-calling)。当前不提供流式输出。

错误码：`CompatibleModelClient` 把传输层与模型返回的原始异常收敛为固定的 `MODEL_*` 前缀，只输出面向用户的中文说明，绝不透传供应商响应体或密钥。平台工程适配器 `OhosJsonTransport` 已抛出 `MODEL_AUTH`（401/403）、`MODEL_RATE_LIMIT`（429）、`MODEL_HTTP`（其它非 2xx）；适配层原样透传这些已分类错误，并对未分类情况补充 `MODEL_TIMEOUT`（超时/中断）、`MODEL_TRANSPORT`（断网/DNS 等），配置非法为 `MODEL_CONFIG`，响应格式不兼容为 `MODEL_RESPONSE`。

上下文裁剪：`AgentEngine` 会把整段历史交给模型，裁剪由适配层负责。`CompatibleModelClient` 接受可选的 `ModelClientOptions.maxContextChars`（默认 `DEFAULT_MAX_CONTEXT_CHARS = 24000`），发送前用 `trimContext` 按字符预算裁剪。裁剪始终保留开头的 system 消息，并以“assistant 工具请求 + 其全部 tool 结果”为整组从最早历史丢弃，保证送入模型的历史里不会出现未配对的调用或孤立结果。

## 三、Agent 工具

```typescript
interface AgentTool {
  definition(): ToolDefinition;
  execute(input: string, context?: ToolExecutionContext): Promise<ToolResult>;
}
```

`ToolDefinition` 含唯一名称、说明和 `parametersJson`（JSON Schema）。工具返回 `{ name, success, content }`，无法完成时明确返回 `success: false`。工具注册表捕获未处理异常并返回失败结果。

示例 `create_study_plan` 输入：

```json
{"goal":"复习高数","days":3}
```

`goal` 为 1–200 字，`days` 为 1–30 的整数。应用运行时会将基础计划保存到学习仓库，同时返回文字安排；未注入仓库的独立工具示例仅返回文字。该工具不创建日历事项或提醒。2026-11-11 新增独立日历草案工具和应用确认流程，见第八节。

`ToolExecutionContext` 含引擎传递的 `conversationId`，注册表透传给工具；旧工具可继续只接收 input。日历工具使用真实上下文，不从模型输入接收会话归属。

## 四、会话仓库

```typescript
interface SessionRepository {
  list(): Promise<Conversation[]>;
  get(id: string): Promise<Conversation | null>;
  save(conversation: Conversation): Promise<void>;
  delete(id: string): Promise<void>;
}
```

`Conversation` 含 `id/title/messages/updatedAt`。查询按最近更新时间排列；不存在的 ID 返回 `null`。`JsonSessionRepository` 使用 `KeyValueStore`，应用内共用一个实例并串行化写入，避免并发保存覆盖其他会话。

设备装配用 `FileKeyValueStore`，落到 `context.filesDir/campus_agent_sessions_v1.json`；先写临时文件、同步后重命名。错误与不兼容版本向上传递，不悄悄清空历史。此轻量方案每次读写整份文件，正式数据量扩大后由 C 迁移数据库和上下文裁剪。

内存存储仅用于开发检查；Node 文件端口检查只验证公共仓库协议，不能代替两端重启实测。

`StudyDataRepository` 复用同一个 `KeyValueStore`，但用独立 key `study_data_v1` 存储学习计划与打卡记录（`UserConditions/PlanTask/PlanVersion/StudyRecord`），落到 `context.filesDir/campus_agent_study_data_v1.json`，与会话文件互不覆盖。写入同样串行化并使用快照；文档损坏或版本不兼容时抛 `STORAGE_CORRUPT` 而不清空历史，找不到计划或任务时抛 `STUDY_NOT_FOUND`。

## 五、平台语音与 HTTP

```typescript
interface SpeechService {
  isAvailable(): boolean;
  recognizeOnce(): Promise<string>;
  speak(text: string): Promise<void>;
  stop(): Promise<void>;
}

interface JsonTransport {
  post(request: JsonRequest): Promise<string>;
}
```

ASR 返回文本后由 B 调用同一个 Agent 入口；TTS 失败只影响语音，已经生成的文字仍可读。`recognizeOnce` 应在成功、拒绝授权、取消、超时和失败时结束 Promise；`stop` 需释放平台资源。鸿蒙语音实现由你负责，Android 语音初期可返回不可用。

现有实现通过 `createPlatformSpeech(context)` 创建服务，注入 `createDeviceRuntime(context, settings, speech)`；公共接口保持不变。`isAvailable()` 表示 ASR/TTS 系统能力均已声明，最终服务可用性由实际调用确认。`speak()` 等到播放完成才结束；`stop()` 使等待中的操作以 `SPEECH_CANCELLED` 结束。并发返回 `SPEECH_BUSY`；识别整体超时 30 秒，播报超时 120 秒。详细配置、自测工程和协作步骤见[语音开发与联调](语音开发与联调.md)。

`JsonRequest` 为 `url/body/bearerToken`，平台工程负责人的系统 HTTP 适配器负责把 token 放到 Authorization 头中，响应文本交给 C 解析。不要打印请求头或把凭据放入聊天记录。

## 六、依赖装配与协作规则

- `createMockRuntime()`：模拟模型 + 内存历史，供无需设备的开发检查。
- `createDeviceRuntime(context)`：模拟模型 + 本地文件历史，供早期双端页面联调。
- `createDeviceRuntime(context, settings, speech)`：云模型 + 本地历史 + 指定语音服务；settings 由 C/B 接入，speech 由你提供并与 B 对接。
- 修改接口时，提供最小调用样例；平台包依赖只出现在适配器，A 的 Agent 纯 TS 保持独立。

## 七、整合后的学习数据与模型设置

`AppRuntime.study` 暴露 C 的 `StudyDataRepository`，与会话仓库共用设备 `FileKeyValueStore`，使用独立 key `study_data_v1`。`StudyPlanTool` 在返回成功前保存基础计划，B 通过 `listPlans()` 回看，通过 `setTaskCompletion(planId, taskId, completed)` 原子更新状态与打卡；重复确认完成不会重复打卡，撤销状态保留历史打卡记录。

基础计划的 `dailyMinutes: 0`、`startDate: ''` 表示尚未设置时长和实际日期。全部学习计划独立于会话，删除会话保留计划；新增的系统日程 ID 映射保存在独立的 `calendar_data_v1`。

UI 空闲时调用 `configureDeviceModel(runtime, settings)` 应用真实模型；不传 settings 切回离线模型。它先校验配置再调用 `runtime.replaceModel`，保留会话、学习仓库和语音实例。API Key 仅在本次运行驻留，不持久化。C 的 `maxContextChars` 默认 24000，按工具请求与结果分组裁剪上下文。

## 八、日历草案与平台端口（2026-11-11）

公共类型在 `contracts/Calendar.ts`。`CalendarService` 提供 `isAvailable()`、`unavailableReason()`、`requestPermission()`、`findEvent(entry)`、`createEvent(entry)`；后两者返回 `CalendarEventReference {calendarId, eventId}` 或查询无结果的 null。查询失败必须抛错，不可按“未找到”处理。

`AppRuntime.calendar` 暴露协调器。装配方式为 `createRuntime(model, store, speech, modeLabel, calendarService?)`；设备端为 `createDeviceRuntime(context, settings?, speech?, calendarService?)`。新增参数均在末尾，旧调用兼容。共享页面通过 `createPlatformCalendar(context)` 注入服务，模型切换保留协调器。

模型可调用 `prepare_calendar_events` 准备草案、`list_calendar_drafts` 查询当前会话的同步记录，以及 `list_study_plans` 读取计划/任务 ID。草案支持最多 30 条、北京时间、明确带偏移量的时间、提醒及可选的计划任务关联。`success: true` 表示草案准备成功，不能解释为已写入日历。

仅真实 UI 确认调用 `confirm(draftId, revision)`；编辑调用 `edit(draftId, revision, eventId, input)`；取消调用 `cancel(draftId, revision)`。旧 revision 返回 `CALENDAR_STALE`。`AgentState.completed` 仍仅代表一轮 Agent 结束，日程执行状态独立存储：`pending/writing/created/failed/uncertain`。仅 created 带成功的系统 eventId。

数据 key 为 `calendar_data_v1`，损坏时返回 `CALENDAR_STORAGE` 并保留原始文件。未授权为 `CALENDAR_PERMISSION`，无平台实现为 `CALENDAR_UNAVAILABLE`。确认后逐条写前落盘，系统返回 ID 后再落盘；恢复重试先查询稳定 identifier，避免重复创建。具体界面、验证和限制见[系统日历接入与验收](系统日历接入与验收.md)。
