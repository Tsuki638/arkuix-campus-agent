# 四人分工与里程碑

## 分工原则

你负责 A：Agent 核心。其余三位先以 B/C/D 代称，可直接替换为真实姓名。

按业务层分工，四人围绕同一份 ArkTS/ArkUI 源码协作；鸿蒙和 Android 共享核心代码。平台差异集中在适配层和工程配置。

**产品方向已确定为“大学生学习方向与行动规划 Agent”。** 围绕考研、就业目标，完成“方向访谈 → 路径选择 → 阶段计划 → 日程预览与确认 → 写入设备日历 → 进度反馈与调整”。产品定位与新增任务以 [README](../README.md) 和本文件为准。

以下为新增开发任务，均需后续实现与验证；现有 `StudyPlanTool` 仍是按目标和天数生成文字安排的最小示例。

| 成员 | 与产品方向对应的新增工作 |
| --- | --- |
| A：Agent | 设计渐进式方向访谈与候选路径，扩展任务拆解和约束排期，处理写入前确认及反馈后的重新规划 |
| B：UI | 提供考研/就业入口、路径选择、应用内计划书、周日程预览、批量确认和任务完成反馈 |
| C：模型与数据 | 接入真实模型，持久化用户条件、选定路径、计划版本、任务进度与系统日程 ID 映射 |
| D：平台 | 验证并实现双端日历适配、权限与结果反馈，继续完成鸿蒙语音和双端构建安装 |

## A：你，Agent 核心

**负责目录：** `app/entry/src/main/ets/agent/`。公共 `contracts/` 的变更由你汇总，修改前与 B/C/D 对齐。

任务：

1. 围绕考研与就业目标，定义专业、年级、基础、兴趣和可用时间等访谈条件，写清候选路径、工具动作与结束条件。
2. 完善 `AgentEngine`：多轮上下文、任务状态、工具选择、结果回传和最大步数。
3. 扩展 `StudyPlanTool`，输出带预计耗时、依赖和完成标准的任务，并结合可用时段排期；日历工具调用需包含预览确认、执行结果与重试去重。
4. 对参数错误、未知工具、模型失败、循环调用给出可理解的处理；避免宣称未完成的工具已成功。
5. 写一段可演示的多轮任务脚本和一页流程说明，给 B 提供界面状态，给 C 提供工具 schema。

交付物：Agent 核心代码、至少一个场景工具、流程及失败说明、相应行为检查、30–60 秒 Agent 演示片段。

验收：连续两轮输入保留上下文；能展示“模型请求工具 → 执行 → 结果回传 → 最终答复”；工具失败和执行超限能停止并提示下一步。

独立开发方式：使用 `MockModelClient`、内存仓库和 `npm.cmd run demo`，不必等 C 的真实模型接口。

## B：共享 UI 与交互

**负责目录：** `ui/`、`pages/`、后续共享 UI 资源。B 不另建 Android UI。

任务：

1. 完善文本对话：消息列表、发送、等待状态、工具执行反馈、失败提示和键盘体验。
2. 完善会话管理：历史列表、打开、新建、删除确认；当前框架已有基本交互。
3. 展示候选方向与理由、阶段计划和周日程，补齐日历写入预览确认及完成/未完成反馈；统一颜色、字体、间距、空态。
4. 增加运行时模型设置入口，与 C 对接模型地址/名称/密钥；密钥不写入会话历史。
5. 对接 D 的语音状态、权限提示和播报入口，保持两端文本主路径体验一致。

交付物：共享页面与组件、关键页面截图、交互说明、两端 UI 检查记录。

验收：两端使用同一页面代码完成文本对话和历史操作；加载/空态/错误可见；用户看得懂 Agent 是否在调用工具；不依靠控制台完成主流程。

独立开发方式：使用现有模拟模型和固定会话样例。原生工程未就绪时先编辑共享组件；D 完成 M0 后使用 DevEco 预览及设备调试。

## C：模型与数据服务

**负责目录：** `services/model/`、`services/storage/`，以及与这些行为对应的检查用例。

任务：

1. 选择一种可用的云端模型，完成真实多轮对话；若使用工具调用，确认所选模型及接口支持对应协议。
2. 基于 `CompatibleModelClient` 接入服务，保持 `ModelClient` 接口稳定；处理供应商参数差异、空回复、异常格式、鉴权失败、限流和超时。
3. 接收 B 的运行时配置，在装配点替换模拟模型；向 D 提供网络、域名、权限需求。
4. 完善本地 JSON 历史仓库；在鸿蒙和 Android 上验证重启恢复、回看、删除，保留损坏数据并提示失败。
5. 记录模型服务及来源，不记录密钥；控制上下文长度，避免历史无限增长导致请求失败。
6. 扩展用户条件、学习路径、计划版本、任务状态和系统日程 ID 映射的持久化，保持计划书与日程使用同一份任务数据。

交付物：真实模型适配、服务配置说明、本地存储实现、模型异常处理记录、双端历史恢复与删除证据。

验收：两端至少一次真实模型调用；第二轮能引用上一轮信息；退出重启后历史存在；删除后重启也不会恢复已删除会话；真实服务错误能通过接口传给 UI。

独立开发方式：假 HTTP 端口和内存/文件端口检查已提供。先验证模型协议和历史仓库，再与 D 的系统 HTTP/文件 API 联调。

## D：平台能力与工程交付

**负责目录：** `platform/`、`scripts/`、官方生成的 `AppScope/`、构建文件、Ability、`.arkui-x/` 宿主和签名/权限配置；统一工程参数。

任务：

1. **优先打通两端空框架。** 统一 DevEco/SDK/ACE/JDK/Android SDK 版本，在 M0 就产出鸿蒙及 Android 的首次构建记录。
2. 执行官方模板初始化，确认 `entry` 的 ArkUI-X 配置；验证 `@ohos.net.http` 与 `@ohos.file.fs` 在所用 SDK 两端可用，处理必要的插件/宿主配置。
3. 实现鸿蒙 `SpeechService`：麦克风授权 → ASR → 返回文本；模型结果 → TTS；停止识别/播报及生命周期释放。
4. 将鸿蒙专用语音依赖隔离在平台实现中，通过所选 SDK 支持的方式选择适配器，保证 Android 编译路径不会强行依赖鸿蒙专有 Kit。
5. 补齐两端权限、签名、安装与运行步骤，汇总 HAP/APK、设备信息、构建日志与演示材料。
6. 验证所选 SDK 的日历接入方式，提供统一日历端口的鸿蒙与 Android 适配，处理权限、平台桥接、逐项执行结果和本应用日程的更新。

交付物：统一环境记录、鸿蒙 ASR/TTS 实现、权限与平台适配、双端构建/安装说明、安装包或课程允许的运行说明。

验收：同一代码库构建并安装两端；鸿蒙演示“ASR → Agent/模型 → TTS”；拒绝权限后仍能使用文本；停止或离开页面时释放语音资源；Android 文本主流程可用。

独立开发方式：最初使用模拟模型打包，不等待真实云服务；语音先实现 `SpeechService` 后注入装配点。

## 接口与文件归属

| 交界点 | 提供者 → 使用者 | 约定 |
| --- | --- | --- |
| `AgentService` | A → B | UI 只传会话 ID/文本，接收状态和结果 |
| `ModelClient` | C → A | 统一内容与工具请求，不暴露供应商响应体 |
| `AgentTool` / 工具 schema | A → C | A 校验参数和执行，C 传递调用与 ID |
| `SessionRepository` | C → A/B | A 保存对话，B 查询和删除；应用内共用一个仓库实例 |
| `JsonTransport` | D → C | 系统网络 API、权限和超时由适配器处理 |
| `SpeechService` | D → B | 识别输出仍走同一个 Agent 文本入口 |
| 拟新增日历端口 | D → A/B | A 发起工具动作，B 预览确认，D 执行；C 持久化任务与日程 ID 映射，接口待协商 |
| `bootstrap/` | A/B/C/D 协商 | 仅做装配，替换实现的人同步其他成员；避免同时编辑 |

每人可以使用 `feat/agent`、`feat/ui`、`feat/services`、`feat/platform` 分支。每个合并请求尽量只改自己目录；公共接口变更同时附调用方改法。D 生成的官方工程配置应尽早合并到公共分支，避免四人各自创建不同模板。

## 课程基线建议节奏：约 6 个工作日，可按实际课期调整

| 节点 | A：你 | B：UI | C：模型/数据 | D：平台/交付 | 联调结果 |
| --- | --- | --- | --- | --- | --- |
| M0，首日 | 细化已定方向、冻结首版接口 | 确定页面及主交互 | 选定模型、确认工具协议 | 生成统一工程、尝试两端首次构建 | 四人拿到同一工程和接口 |
| M1，第 2–3 日 | 跑通多轮 + 一个工具 | 模拟数据下跑通聊天和历史 | 真实模型 + 本地仓库 | 鸿蒙 ASR/TTS + 权限 | 各模块能单独演示 |
| M2，第 4 日 | 接真实工具请求和失败路径 | 接真实 Agent、数据和语音 | 两端模型/存储联调 | 两端安装 + 鸿蒙语音联调 | 完成全部基线闭环 |
| M3，第 5–6 日 | 优化场景和演示脚本 | 优化视觉、异常及反馈 | 排查稳定性与上下文问题 | 冻结版本、打包并整合材料 | 按验收清单逐项留证 |

上述节奏用于课程基线，新增产品能力按以下里程碑逐项推进，具体工期在接口与设备验证后确认：

| 产品节点 | 交付目标 | 验证重点 |
| --- | --- | --- |
| P1：方向与路径 | 考研/就业入口、渐进访谈、候选路径与用户选择 | 信息不足能澄清，推荐有理由，选择可修改 |
| P2：计划与排期 | 两到四周的任务、未来一周的日程、应用内计划书 | 任务有耗时与完成标准，排期符合用户时间约束 |
| P3：日历执行 | 双端预览确认、日程写入与结果反馈 | 确认前无写入，重试不重复创建，拒绝权限仍能查看计划 |
| P4：反馈与调整 | 完成/未完成反馈、重新排期、确认更新关联日程 | 计划与日程一致，仅操作本应用创建的日程 |

保留两个场景入口，先选团队熟悉的一条专业路径完成 P1–P4，再扩展内容深度。课程基线与本项目首版目标完成后，考虑计划书导出、Android 语音、更多专业或其他设备应用接入；iOS、RAG、多模型切换后续扩展。

## 每个人现在就能开始的事

- A：围绕已定方向写 3 组访谈/路径/工具结果样例，覆盖条件不足、时间冲突和未完成后的调整。
- B：基于 `ChatWorkspace.ets` 设计方向选择、计划与日程预览，补删除确认、设置入口及录音反馈。
- C：申请/使用已有模型服务，在不提交密钥的前提下验证模型协议，然后检查两端本地历史。
- D：安装并记录 SDK 组合，运行初始化和构建脚本，先报告两端能否打包。
