# 从离线演示到学习规划 Agent

本页记录 2026-11-11 的升级路线。当前分支已接入阶段计划、模型任务草案校验、约束排期、进度和鸿蒙确认流程。最新运行方式与待验收项目见 [A 实现与交接](Agent学习方向与行动规划说明.md)。

## 现有基础

- `AgentEngine` 已有多轮会话、模型与工具执行循环、工具结果回传、执行步数限制、并发保护和失败反馈。
- `CompatibleModelClient` 已映射 Chat Completions 的消息与工具协议；`OhosJsonTransport` 已实现设备 HTTP 请求和鉴权头。
- 会话、基础计划和打卡已有本地仓库，界面已接模型设置、计划回看与完成状态。
- 当前启动时未传模型配置，默认创建 `MockModelClient`；应用模型设置后，本次运行可以使用云端适配器。重启后默认回到离线模式。
- 当前已注册 `create_study_plan`、`prepare_calendar_events`、`list_calendar_drafts` 和 `list_study_plans`。基础计划仍使用模板任务；日历工具可准备明确时段的草案并读取执行记录，鸿蒙端由用户确认后调用系统接口，设备效果待验收。

工具调用需要模型返回工具名称与参数，由应用执行并将结果送回模型继续处理。现有循环已经覆盖这种基本交互，参考[百炼 Function Calling 官方说明](https://help.aliyun.com/zh/model-studio/qwen-function-calling)。

## 第一阶段：设备上的真实模型与工具闭环

使用支持当前工具协议的模型，在应用“模型设置”中填写完整 HTTPS Chat Completions 地址、模型名称和 API Key。地址和模型 ID 以服务商当前控制台与官方文档为准，不使用占位地址。

验收应覆盖自然语言输入 → 模型选择工具 → 工具执行并保存 → 结果回传 → 最终答复 → 计划页回看。只显示云端文字回复尚不足以证明工具闭环通过。现有 `npm.cmd run verify:model` 可通过环境变量执行真实模型验证，但使用 Node 传输端口，设备 HTTP 仍需单独验收。

2026-11-11 已接入 DeepSeek 官方非思考模式，并通过 `npm.cmd run verify:deepseek` 完成 3 次真实 HTTP 请求：生成并保存 3 天高数计划、回传工具结果、第二轮记住科目与天数；另验证仓库序列化恢复。应用设置页已加入官方配置入口。详细记录见 [DeepSeek 接入与验证](DeepSeek接入与验证.md)；设备网络与重启恢复仍待验收。

修改入口：`bootstrap/DeviceRuntime.ets`、`services/model/CompatibleModelClient.ts`、`ui/ModelSettingsPanel.ets`。不同模型可能要求额外参数或保留推理相关字段，当前适配器需按选定模型验证，不能假设所有兼容接口行为相同。

可以保存接口地址、模型名称等非敏感偏好；密钥沿用运行时输入，或在确定平台方案后接入安全凭据存储。面向其他用户发布时，再引入后端鉴权、服务商密钥管理、配额与用量控制。

## 第二阶段：可用的学习规划 Agent

| 优先项 | 建议改变 | 验收例子 |
| --- | --- | --- |
| 条件访谈与记忆 | 持久化专业、年级、已有基础、目标、截止日期、每日时长、可用时段和已选路径；逐步补齐缺项 | 用户只说“想找实习”时先了解条件，后续会话能使用已确认信息 |
| 具体学习内容 | 用模型生成结构化任务草案；每项包含内容、耗时、完成标准和前置任务；代码校验后保存 | 任务出现具体章节、练习或项目产出，而非重复“完成第 N 部分” |
| 约束排期 | 检查任务依赖、总时长、可用时段和截止日期；条件冲突时澄清或提出调整 | 每晚只有 1 小时，就不会安排 3 小时任务 |
| 查询与调整工具 | 注册查询已有计划、读取完成情况、记录进度、生成修订草案等工具 | 用户说“昨天没完成”时，先读取真实计划和进度，再提出调整 |
| 过程与确认交互 | 增加访谈、草案、待确认、执行中、完成和失败等状态；显示工具动作与结果 | 用户能看到将保存或修改哪些任务，并确认具体变更 |

建议的实现边界：模型负责提出方向与任务草案，工具负责校验、保存、查询和实际操作。目标、时间、任务结构和工具结果使用明确字段，不依赖从聊天文本中猜测状态。

主要修改 `agent/AgentEngine.ts`、`agent/tools/StudyPlanTool.ts`、`contracts/Models.ts`、`contracts/Ports.ts` 和 `services/storage/StudyDataRepository.ts`；公共数据变更需同步调用方，并迁移已有本地数据。

## 第三阶段：系统日历与持续执行

新增统一日历端口与鸿蒙、Android 平台适配。先展示具体日期、起止时间与提醒设置，用户确认后执行；保存任务 ID 与系统日程 ID 的映射。日历读取获授权后检查冲突，未授权时使用用户提供的可用时段。

2026-11-11 已实现统一端口、鸿蒙创建适配、应用预览编辑与确认、稳定标识去重和记录恢复；已完成 50 项测试及 DeepSeek 真实草案/查询联调。设备实际创建与提醒、Android 桥接、已有日程修改及冲突检查仍待实现或验收，见[系统日历接入与验收](系统日历接入与验收.md)。

为新增与更新操作增加去重标识、逐项结果、失败重试和中断恢复，只更新本应用创建的日程。用户反馈完成、未完成或时间变化后，读取当前状态并生成修订方案，再确认需要变更的日程。

招生要求、考试科目、岗位要求等需要外部依据时，再加入受控检索，保留来源、适用年份和查询时间；本地已有资料可作为补充。

## 建议开发顺序与完成标准

先完成设备真实模型工具闭环，再实现条件记忆、具体任务草案及查询修改，随后接日历确认与反馈调整。流式输出、知识库和更多模型可在核心流程稳定后加入。

一个可复现的完整演示：用户说明基础和空闲时间 → 助手澄清必要条件 → 比较并确认学习方向 → 生成具体的两周计划 → 预览未来一周日程并确认 → 写入设备日历 → 标记一项任务完成或未完成 → 读取进度并调整后续安排 → 重启后恢复计划与执行状态。

当前已完成 Node 环境中的 DeepSeek 真实工具调用；设备上的模型工具闭环、日历写入及完整产品流程，仍需平台适配和设备联调证据后才能计为完成。
