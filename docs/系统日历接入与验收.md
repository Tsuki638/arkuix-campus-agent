# 系统日历接入与验收

2026-11-11 新增首版日历功能：真实模型准备草案、应用预览与编辑、用户确认、鸿蒙系统日历创建、逐项结果和系统 ID 持久化。Android 当前返回不可用提示，尚未实现原生桥接。设备日历写入和提醒效果仍需设备验收。

## 应用内使用

有两种草案入口：

1. 在模型设置中连接 DeepSeek，再发送“请准备明晚 19:00 到 20:00 的高数复习日程，提前 10 分钟提醒，先给我预览”。工具结果旁点击“预览日程并确认”。
2. 在“学习计划”中选择“准备日历日程”。待完成任务会按明天开始、原任务第 N 天、每日 19:00–20:00 生成可编辑草案，默认提前 10 分钟提醒。页面会明确展示这些默认值。

进入侧栏“日程预览”，逐项检查标题、完整日期、起止时间和提醒。尚未尝试写入的草案可以点击“修改”，时间格式为 `YYYY-MM-DD HH:mm`；提醒分钟用英文逗号分隔，留空表示不提醒。保存后重新预览，点击“确认添加 N 条日程”。

确认时才申请日历读写权限。鸿蒙端在本应用的本地日历账户“学习计划”中创建日程，系统实际返回有效 ID 后才显示创建成功。离线模型模式也可使用计划页入口；确认按钮仍会执行真实系统写入。

一批最多 30 条，单条最长 24 小时，开始时间须晚于当前时间；首版固定为北京时间 `Asia/Shanghai`、明确的 `+08:00` 时间。提醒最多 3 个，范围为提前 0–10080 分钟。

权限拒绝时保留草案。部分条目未完成时显示各条状态，可以“查询并重试未完成项”；已创建条目保留原系统 ID。取消草案只停止后续执行，已发生的系统写入继续保留；结果不确定的条目需要查询重试或在系统日历中核对。

已尝试执行的草案不再提供编辑；当前尚未实现修改、删除已创建的系统日程、重复规则、跨时区排期或其他日程的冲突检查。系统提醒是否实际触发还受日历账户、系统通知与设备设置影响。

## 实现边界

| 位置 | 职责 |
| --- | --- |
| `contracts/Calendar.ts` | 草案、事件、系统引用、平台接口、工具执行上下文 |
| `services/calendar/CalendarCoordinator.ts` | 参数校验、草案版本、串行确认、写前与写后持久化、重试与去重 |
| `services/calendar/CalendarTime.ts` | 北京时间显示、日期校验、计划默认时段 |
| `agent/tools/CalendarTools.ts` | `prepare_calendar_events`、`list_calendar_drafts`、`list_study_plans` |
| `platform/calendar/HarmonyCalendarService.ets` | 权限申请、应用自身日历账户查询与创建、系统日程查询与创建 |
| `platform/calendar/PlatformCalendarFactory.ets` | 先判断平台与系统能力，再延迟加载鸿蒙专有模块 |
| `ui/CalendarPanel.ets`、`CalendarDraftCard.ets` | 草案、逐项编辑、真实确认、取消、执行结果和重试 |
| `bootstrap/Runtime.ts`、`DeviceRuntime.ets` | 注入同一份存储和平台端口，切换模型保留日历协调器 |

Agent 工具只获得准备和读取能力，没有模型可调用的确认或直接写入工具。`ToolExecutionContext.conversationId` 由引擎传递，不使用模型声称的会话 ID。模型中的 `confirmed: true` 或聊天回复“同意”都不会执行写入。

确认调用 `CalendarCoordinator.confirm(draftId, revision)`，绑定当前预览版本；编辑后旧版本不能提交。界面执行结果以“应用执行结果”保存到原会话，下一轮模型可读取；模型也可调用只读工具查询本地同步记录。该查询不实时核对用户在系统日历中后续手动修改或删除的结果。

独立存储 key 为 `calendar_data_v1`，设备文件为 `context.filesDir/campus_agent_calendar_data_v1.json`。记录包含会话、计划、任务、日历账户与系统日程 ID，原有 `study_data_v1` 无需迁移。删除会话不删除日程或其同步记录。

每条事件先保存 `writing` 状态再调用系统接口，使用稳定的 `identifier` 查询已有事件。创建成功但本地保存失败时，下次显式重试先查询并恢复原 ID；查询失败时不贸然创建。取消部分草案后，其已创建或结果不确定的计划任务仍受到去重保护。

鸿蒙实现依据 [Calendar Kit 官方接口](https://developer.huawei.com/consumer/cn/doc/harmonyos-references/js-apis-calendarmanager/)，声明并按需申请 `READ_CALENDAR` 与 `WRITE_CALENDAR`；只访问应用自己的日历账户，未申请整个日历的读写权限。当前使用 API 24 SDK，系统回读的 `identifier` 用于恢复。

## 已完成的验证

```powershell
npm.cmd run check
npm.cmd run verify:calendar
```

`check` 已通过 50 项测试，其中新增 15 项日历测试，覆盖草案不写入、真实会话隔离、时间校验、编辑后旧确认失效、并发重复确认、权限拒绝、部分失败、结果丢失、落盘失败恢复、取消、去重、损坏数据保护与模型切换。

`verify:calendar` 从被忽略的 `.env.local` 加载已有 DeepSeek 密钥，会产生真实 API 用量。2026-11-11 实际验证共 4 次 HTTP 请求：真实模型准备了日期、19:00–20:00 时段及提前 10 分钟提醒均正确的单条草案；第二轮调用查询工具返回 pending，所有系统 ID 保持 0；草案可以从序列化数据恢复。报告位于 `.generated/deepseek-calendar-verification.json`，不含密钥。

该命令注入不可用的设备日历端口，只证明真实模型与草案/查询协议，不代替系统写入。测试中的创建、权限和中断恢复使用模拟日历端口。

原生 API 24 ArkTS 编译及未签名 HAP 打包通过。鸿蒙专有日历模块会出现跨平台支持警告，已通过平台工厂隔离；这不能作为 Android 日历可用的证据。

## 设备验收步骤

1. 在 DevEco 中运行更新后的 `app/`，从计划页准备一条草案，修改为便于核对的未来时段。
2. 点击确认并拒绝权限，检查草案保留且没有成功提示；随后允许权限，再次确认。
3. 检查应用显示成功，打开系统日历，找到“学习计划”账户中的同一标题、日期、起止时间与提醒。
4. 刷新或重复操作，确认没有重复日程；退出重启应用，确认同步记录恢复。
5. 安排几分钟后的日程，核对系统通知与日历设置，验证提醒是否实际触发。
6. 让真实模型准备草案并完成确认，回到对话询问执行结果，核对查询记录与系统日历一致。

本次已连接 API 24 模拟器 `127.0.0.1:5555`，覆盖安装更新后的 HAP，保留原应用数据；已验证计划页入口、三天草案生成、预览与编辑保存、系统日历权限弹窗、拒绝权限后零创建，以及重启后从设备文件恢复三条待确认草案。截图位于 `.generated/calendar-device.png`，权限弹窗截图位于 `.generated/calendar-permission.png`。权限弹窗的应用模板名称随后已改为“学习规划助手”。

本次没有授予日历权限，没有执行实际系统日程创建。上述步骤中的允许权限后的创建、系统日历核对、提醒触发、真实模型与设备写入的完整往返仍待验收。Android 的 Calendar Provider 与桥接待另行实现和验证。
